#### 1. P0：上线前必须做（会丢玩家东西、会被拒审、会被打穿）

**F1 存档写入没有 CAS，只读意图也走全套写盘。**（✅ 已落地 2026-10-06，含一处真实 MySQL 死锁；见文末） 证据：`game/DbGameStore.java:40` 用 `saves.put(uid,node,null,true)`——`force=true` 直接绕过 `SaveService.java:52` 的冲突分支；`GameService.act`（`:73→87`）的 load→mutate→save 之间既没事务也没锁；客户端 `state.js:47/63` 存了 `revision` **却从不上送**，而 `panels.js:1528` 的关于页明明白白写着"revision 乐观并发"。后果有两层：同一账号两台设备（手机 + 平板，或卸载重装）各写各的，后写的整帧把先写的抹掉，玩家看到的是"我练了一半的东西没了"；更硬的一条是 `AdService.settle` 在 `act` 开头就把工单 `markSettled`（`AdService.java:257`），随后写盘失败或被并发覆盖 ⇒ 广告看完了、奖励记在一份作废的帧里，**永久丢**。最小改法：`UPDATE user_save SET payload=?,revision=revision+1 WHERE user_id=? AND revision=?`，0 行就重读重放（有界 3 次）；`settle` 挪进同一事务，或者"写盘成功后才置 settled"；纯读意图走一条不落盘的 `actReadOnly`，历史只在 `reset`／后台改档／回滚时记（或每 N 版抽样记一条）。回归：JUnit 用 `MemGameStore` 并发两个 `act()` 断言金币与积分之和不多不少；e2e 补"只读意图不新增 revision"；`SaveMigrationsTest` 补"markSettled 后写盘失败，工单必须回到 pending"。

**F2 意图没有幂等标识**（followups 第 7 项，一直没做的那条）。（✅ 已落地 2026-10-06，键的口径与方案有一处偏离，理由写在文末第 8 节；见文末）`POST /api/game/{intent}` 不带任何客户端序号，服务端也不看。C4 只解决了"**客户端**别主动重放写意图"，管不了链路层重发——4G 上"服务端已执行、响应没回来"是常态，重发一次就是两次入账、两次扣耗材。改法：意图带会话内单调 `seq`，服务端按 `(uid,seq)` 缓存最近 N 帧结果，重复 seq 直接回缓存帧。回归：e2e 同一 seq 连发两次 `market.buy`，断言只扣一次且两次返回**逐字相同**的帧。

**四处与方案不同的判断。** ① 方案里写的行号（`Moderation.vue:300,322`）是旧的，真正编造总数的是 `:91`/`:113`——按文本找公式而不是按行号找代码。② `/config` 一旦分页，就得同时给搜索框：面板原先有三处靠"整表都在内存里"办事（同名预检、409 后重开、定位某个键），分页会把它们静默降级成"只在前 20 行里找"，所以这三处都改成带 `q` 的服务端预检（真正的守门仍是 `expect=none` 那个 409，预检只是把话说明白）。③ 缓存失效用**版本号**而不是 TTL：TTL 到点会重扫，运营改完内容却可能看到上一版体检结果，而"我改了没生效"正是这一轮要消灭的那类误判。④ `total` 与页长都是服务端说了算，客户端的 `size` 只做展示选择——把 200 这个上限同时写进 `Page.MAX_SIZE` 和 `admin-paging.js` 的判据里，谁想调就必须在两处一起动。

**验收基线**：`node test/validate.js` PASS（新增 `admin-paging` 一行）、JUnit **507 / 0 失败**（**50** 个类，本轮 +`AdminPagingHttpTest` 6、+`ContentHealthServiceTest` 11、`MapperQueryHygieneTest` 8→11）、`test/e2e-api.sh` **PASS=495 / FAIL=0**（+14 条 H6-3 断言，全文 `server/logs/e2e-latest.log`）、`test/admin-dist-check.sh` 产物同源（22 个产物逐文件 sha256 相同）。本轮没动 `frontend/` 与壳，`?v=3.14` 与 APK 重出仍随收尾那一批一起做。

**没验到的，写清楚**：① 后台登录的**真口令人工走查**依旧没做（同第 9 节那条纪律），分页控件的观感——每页 20 行时页码条的位置、搜索框清空后的行为——只按 DOM 与接口形状核对过，没在真屏幕上点过。② 本机库里 `sensitive_word` 是空表、`app_config` 只有 21 个键，所以"翻页不重不漏"是在小数据上跑的；这条判据真正的价值要等运营把词表填到几百条才显出来，而 `ORDER BY` 那条静态尺子在 CI 上每次都判，不依赖数据量。③ `/dashboard` 的趋势与 `/analytics` 一类"读多张表"的面板没有进这一轮的分页账（它们本来就不是行列表），H6 ④—⑥ 仍在待做。④ `Page.off` 把负数当 0、`Page.size` 把超限压到 200 是**静默归一**：面板不会知道自己被改了参数，只有体检与审计看不出来；如果将来要做"参数错了就 400"，得连着 `admin-paging.js` 的页长判据一起改。
